# NEXA: вход по временному паролю с обязательной сменой (Вариант A)

## 1. Как вход устроен сейчас

- Основа входа — Supabase Auth: email и пароль. Сессия хранится в браузере.
- Страница `/auth`: вход через `signInWithPassword` и **открытая самостоятельная регистрация** через `signUp`. В коде остались отладочные записи в консоль `AUTH DEBUG`. Пароль в них не попадает, но саму отладку стоит убрать.
- Главная страница `/` (`src/routes/index.tsx`): после входа вызывает `ensureProfile` (функция `ensure_my_profile`), затем `getCurrentProfile`, затем `getAdminAccess`. Функция `ensure_my_profile` создаёт профиль и роль employee, если их нет, и ставит статус приглашения «принято».
- Права проверяются на сервере: `is_active_user`, `has_permission_for` (роль, уровень доступа, владелец), `nexa_owners`. Правила доступа к таблицам (RLS) построены на этих функциях.
- Admin Panel: `inviteEmployee` вызывает `inviteUserByEmail` и записывает профиль и роль. `updateEmployeePassword` позволяет только владельцу задать пароль через admin API.
- Восстановление пароля для обычных сотрудников отсутствует. Есть только `/owner-reset` для владельца: по секретному коду через `owner-password-reset`.
- Признака «требуется смена пароля» нет нигде.

## 2. Что изменится

**База данных (одна миграция):**
- Новая таблица `public.credential_requirements`:
  - `user_id` — ключ, ссылка на auth.users;
  - `must_change_password` (bool);
  - `issued_at`, `expires_at` — когда выдан временный пароль и до какого времени действует;
  - `issued_by` — кто выдал;
  - `changed_at` — когда пароль сменён.
  - RLS включён. Пользователи не получают права на запись: доступ только у service_role. Пароли в таблице не хранятся.
- RPC `get_my_credential_state()` (security definer): возвращает только флаг и срок для `auth.uid()`.
- Функция `is_active_user` дополнительно возвращает false, пока есть активный флаг `must_change_password`. Это только ужесточает доступ: все правила к таблицам и `has_permission` автоматически закрывают рабочие данные до смены пароля. Нужно убедиться, что `ensure_my_profile` и чтение собственного флага работают и с флагом.

**Сервер (`src/lib/admin.functions.ts` и новый `src/lib/credentials.functions.ts`):**
- `createEmployeeWithTempPassword` заменяет `inviteEmployee` в форме:
  - требует `employees.manage` и сохраняет текущие правила владельца для ролей и уровней;
  - вызывает `auth.admin.createUser` с `email_confirm: true` и паролем;
  - записывает профиль, роль и `credential_requirements`;
  - если какой-то шаг не удался, откатывает всё и удаляет созданного пользователя;
  - если пароль сгенерирован сервером, возвращает его один раз в ответе.
- `reissueTemporaryPassword(userId)` — только для владельца: новый временный пароль, флаг снова включается, все сессии сотрудника завершаются.
- `completeRequiredPasswordChange(newPassword, confirm)` — требует вход и активный, неистёкший флаг:
  - пароль меняется через admin API, проверяется сложность;
  - флаг снимается, записывается `changed_at`;
  - сессии сотрудника завершаются, он входит заново с новым паролем.
- `inviteEmployee` остаётся в коде, но убирается из интерфейса. Удалить его можно позже.

**Интерфейс:**
- `AdminPanel.tsx`: в форме выбор «Задать пароль» или «Сгенерировать». Сгенерированный пароль показывается один раз в окне с кнопкой «Скопировать» и исчезает при закрытии. Он не попадает во всплывающие сообщения, адресную строку или браузерное хранилище. Добавляется кнопка «Выдать временный пароль заново» — видна только владельцу.
- Новая страница `/change-password`: новый пароль, подтверждение, требования к паролю.
- `src/routes/index.tsx`: после `ensureProfile` проверяется `get_my_credential_state`. Если флаг активен, пользователь перенаправляется на `/change-password`, рабочее пространство не отрисовывается. Если срок истёк — экран «Временный пароль истёк, обратитесь к владельцу» и выход из системы.
- `auth.tsx`: убираются логи `AUTH DEBUG`. Самостоятельная регистрация отключается — см. вопрос 1.

## 3. Создание сотрудника и первый вход

```text
Владелец/Admin -> форма -> createEmployeeWithTempPassword (сервер)
  проверка прав -> createUser(email, пароль, подтверждён)
  -> profiles + user_roles + credential_requirements(must_change=true, expires_at)
  -> ответ: userId (+ пароль один раз, если сгенерирован)

Сотрудник -> /auth -> вход с временным паролем
  -> / -> ensureProfile -> get_my_credential_state: must_change
  -> переход на /change-password (данные закрыты и правилами доступа к таблицам)
  -> completeRequiredPasswordChange -> флаг снят, сессии завершены
  -> вход с новым паролем -> рабочее пространство
```

## 4. Безопасность

- Admin API и service-role вызываются только внутри серверных функций и только после проверки вызывающего через `has_permission` или `nexa_owners`.
- Временный пароль хранит только Supabase Auth, в виде хеша. В profiles, логах, сообщениях, адресной строке и хранилище браузера его нет. Ошибки возвращаются без текста пароля.
- Флаг смены пароля может менять только service_role. Пользователь не может снять его сам. Обойти страницу смены через прямые запросы нельзя: `is_active_user` закрывает данные.
- Если сотрудник сменит пароль в обход `/change-password`, флаг останется, и доступ по-прежнему будет закрыт.
- Правила доступа, проверки владельца, уровни доступа и роли не ослабляются. Добавляется одна новая блокирующая проверка.
- Рекомендуется включить проверку паролей по базе утечек (HIBP). Минимальная длина пароля — 12 символов, как сейчас.

## 5. Существующие пользователи

- Миграция данных не нужна. Если у пользователя нет записи в `credential_requirements`, смена пароля от него не требуется. Владелец Денис и все уже зарегистрированные сотрудники входят как раньше.
- Записи создаются только при создании сотрудника по новой схеме или при повторной выдаче временного пароля.
- Сотрудники, приглашённые по почте и ещё не принявшие приглашение (`invitation_status = 'sent'`), остаются как есть. Владелец может выдать им временный пароль по отдельному решению.

## 6. Забытый пароль

- Самостоятельное восстановление через почту не добавляется: в корпоративной схеме пароль выдаёт владелец. Сотрудник обращается к владельцу, тот нажимает «Выдать временный пароль заново».
- Восстановление для владельца через `/owner-reset` не меняется.

## 7. Срок действия временного пароля — нужно ваше подтверждение

Предлагаю **72 часа** с момента выдачи. После этого вход по временному паролю не открывает доступ, нужна повторная выдача. Значение будет задаваться одной настройкой на сервере. Не применяю его без вашего подтверждения.

## 8. Вопросы до начала работы

1. Отключить ли открытую регистрацию на `/auth`? Рекомендую: да, иначе любой человек может создать себе учётную запись с ролью employee.
2. Срок действия временного пароля: 72 часа или другой?
3. Кто создаёт сотрудников: все, у кого есть `employees.manage`, или только владелец? Повторная выдача пароля — только владелец.

## Порядок работ после подтверждения

1. Миграция: `credential_requirements`, `get_my_credential_state`, обновлённая `is_active_user`.
2. Серверные функции создания, повторной выдачи и смены пароля.
3. Страница `/change-password` и проверка флага на `/`.
4. Форма в Admin Panel с показом пароля один раз; повторная выдача пароля.
5. Проверка: существующий пользователь входит без смены пароля; новый тестовый сотрудник проходит первый вход; данные закрыты до смены пароля. Валерию создаёт владелец уже после проверки.
